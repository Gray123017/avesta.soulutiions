AVESTA — HOSTINGER DEPLOYMENT

HOW DEPLOYMENT WORKS NOW

The site deploys from Git. hPanel is connected to this repository through the
Hostinger GitHub App (hPanel > Websites > avesta.solutions > Advanced > GIT),
set to branch main, deploying into public_html. Auto-deployment is ON, so every
push to main reaches the live site within a minute or so.

There is no manual upload step any more. Do not upload a ZIP into public_html;
it would be overwritten on the next push, and it bypasses every check below.

WHAT A DEPLOY DOES AND DOES NOT TOUCH

A deploy resets the files this repository tracks and pulls the current main.
Files the repository does NOT track are left alone. That is what keeps live
data safe:

  left alone (gitignored)   users.php, records_data.php, audit_log.php,
                            enquiries.php, password_resets.php, rate-limit
                            files, documents/* (the uploaded NRC scans),
                            avesta-secrets.php, downloads/* installers
  reset on every deploy     everything else, including documents/.htaccess

Never replace this with an FTP sync that deletes files missing from the source.
It would erase the applicant records, the uploaded documents and the installers
on its first run.

NO CI GATE — READ THIS BEFORE PUSHING

Hostinger's GitHub App integration does not expose a deployment webhook, so a
deploy cannot be made to wait for "Check Hostinger site" to pass. Auto-deploy
fires on the push itself. A commit that breaks the site WILL reach customers.

So: open a pull request, let the checks finish, and merge only when they are
green. Pushing straight to main skips the only protection there is.

To deploy without pushing (for example to re-run a failed deploy), use the
Redeploy button on the GIT page in hPanel.

AFTER A DEPLOY, CHECK

  https://avesta.solutions/                 loads (200)
  https://avesta.solutions/loans.php        loads (200)
  https://avesta.solutions/it.php           redirects to /index.php?page=it
  https://avesta.solutions/documents/       MUST return 403 or 404

The last one matters most. documents/.htaccess is the only thing standing
between applicants' NRC scans and anyone who guesses the URL, and it is a
tracked file, so a bad commit can remove it.

Then sign in as an administrator and confirm users, applications and IT
enquiries are still listed.

OTHER SETUP

Configure notification credentials on the server, not in the repository. No
WhatsApp API credential is shipped in this repository. Confirm PHP upload
limits in hPanel after .user.ini has had time to apply.

BACKUPS

Applications, accounts and uploaded identity documents exist only on this
server. They are kept out of Git on purpose, so a deployment never restores
them and a GitHub clone never carries them.

Two copies, and neither one is optional:

1. Hostinger's own backups, in hPanel. Check the schedule is daily and that a
   backup has actually been taken in the last day. Weekly means losing up to a
   week of applications.

2. Your own copy. Sign in as Super Admin, open Accounts, and use "Download
   backup". It gives you a .tar holding the loan book, the accounts, the audit
   log and every uploaded document, with a MANIFEST.json listing a sha256 for
   each file. Verify against those checksums before you trust a copy.

   The file is NOT encrypted: it holds NRC scans, bank statements and password
   hashes in the clear. Keep it on an encrypted drive, do not email it, and
   delete old copies. The Data Protection Act applies to this file exactly as
   it applies to the server, so it must stay in Zambia.

   Only a Super Admin can take one, and only one every five minutes. Every
   download is written to the audit log as backup.downloaded.

Test a restore before you need one. Take a backup now, unpack it somewhere
safe, and check the files are there and the checksums match. A backup nobody
has ever restored is not a backup; it is a belief.

STANDING CAVEAT

Passing the checks is not a guarantee of production security. Before handling
real borrower identity documents or financial data, test on the live host for
HTTPS, permissions, email and WhatsApp delivery, backups, upload limits,
session behaviour and recovery procedures.

Note also that the Data Protection Act, 2021 requires personal data to be
stored on a server inside Zambia, and sensitive personal data always so.
Hostinger has no Zambian data centre. This is unresolved.
